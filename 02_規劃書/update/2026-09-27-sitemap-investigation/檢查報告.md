## 結論與限制

目前沒有發現需要重寫 sitemap XML、修改 Firebase 轉址或搬移伺服器的證據。可重現的異常位於 Search Console 的 Sitemap 專用擷取／處理／狀態回報流程：報表仍為「未知、無法擷取、0 網址」。Google 即時檢查則能取得並顯示完整 XML。

即時測試使用 Google Inspection Tool，不能視為 sitemap 專用爬蟲已成功；也無法用單次成功排除歷史或間歇性失敗。Google 未提供該次 sitemap 失敗的 HTTP 錯誤碼、請求時間或內部處理日誌，因此尚無法斷言是哪一個 Google 內部子步驟出錯。

## 兩個訊息不可混為一談

網址檢查的「發現方式 → Sitemap」目前另顯示「暫時性處理錯誤」。Google 官方將其定義為報表讀取 sitemap 資料時的暫時問題。這不是本網站 XML 語法錯誤的證據，也不能據此直接解釋另一個 Sitemap 報表的「無法擷取」。

`sitemap.xml` 本身沒有編入網頁搜尋索引，亦不等於 sitemap 提交失敗；不應要求替 XML 本身建立網頁索引。

## 後續處理（待辦，不是已完成）

1. 優先向 Search Console 支援／Google Search Central 社群提供本報告與 Google 即時測試證據，要求確認 sitemap 專用處理是否有排程或處理錯誤。尚未代使用者發送任何訊息。
2. 保持 `/sitemap.xml` 與 robots 指向穩定。這次沒有刪除、重送、改名或重新部署，避免再次重設提交時間而失去可比對紀錄。
3. 若支援無法定位，可做單次受控實驗：從相同建置快照額外生成 `/sitemap-diagnostic.txt`，每行一個相同的公開網址；通過候選版本驗證後僅提交一次。保留原 XML。TXT 成功只代表替代格式／路徑成功，不能單獨證明 XML 格式有錯；兩者皆失敗也不能直接證明整站被封鎖。須記錄相同時間窗的 Google 測試結果再判讀。此實驗尚未執行。
4. 若 Google 提供具體狀態碼，再針對 404（發布／路徑）、403（存取）、5xx／timeout（供應端）、parse error（內容）修正；目前沒有這些錯誤的證據。
5. 驗收標準必須是 Sitemap 報表顯示成功、辨識類型且探索到網址；不是提交成功的彈窗、curl 200 或即時檢查成功。
